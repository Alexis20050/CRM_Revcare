## 2. Detailed Technical Resolutions

### 2.1 Fix 1: Mechanic Work-Order Authorization & Scoped Retrieval

#### Root Cause Analysis
In Tenant A, `TenantWorkspaceForm.OpenWorkOrderAsync` requested `/crm/job-orders/{id}` and `/crm/customers/{id}`. In `TenantPermissions.cs`, `/crm/job-orders` requires `Jobs.Manage` and `/crm/customers` requires `Customers.Manage`. Roles `AutomotiveMechanic` and `DetailingTechnician` only hold `Workshop.Read` and `Tasks.UpdateAssigned`. Consequently, clicking "Print Work Order" triggered HTTP 403 Forbidden errors, and exceptions were silently swallowed by `try { } catch { }`.

#### Backend Implementation (`CRM.api/WorkforceEndpoints.cs`)
A dedicated document retrieval endpoint was added under the workshop route group:
- **Route:** `GET /crm/workshop/jobs/{id:int}/work-order`
- **Route Authorization:** Required policy `"TenantOperations"`. Route path starts with `workshop`, requiring permission `"Workshop.Read"` which all workshop roles (`OwnerManager`, `ServiceAdvisor`, `LeadMechanic`, `AutomotiveMechanic`, `DetailingTechnician`) possess.
- **Record-Level Authorization:**
  - Technicians (`TenantPermissions.Technician(user)`): Query verifies if the user is assigned to at least one task on the job order via `db.TaskAssignments`. If unassigned, the endpoint immediately returns HTTP 403 Forbidden.
  - Task Filtering: For technicians, the tasks query filters to `task.AssignedUserId == userId`. Other technicians' tasks on shared jobs are excluded.
  - Lead Mechanics, Service Advisors, and Owners: Access is permitted for all jobs within the tenant, and all tasks on the job order are included.
- **Data Minimization:**
  - Customer contact digits and email addresses are omitted (only `FullName` is included).
  - All payment records, amounts, and billing summaries are omitted.
  - Returns `jobOrderId`, `estimateReference`, `customerName`, `vehicleDetails`, `intakeNotes` (mapped to domain property `job.InquiryNotes`), `jobStatus`, `businessDetails`, and the filtered task collection.

#### Client Implementation (`CRM_Revcare/TenantWorkspaceForm.cs`)
- `OpenWorkOrderAsync` now directly calls `api.Send("GET", $"crm/workshop/jobs/{jobId}/work-order")`.
- Silent `try { } catch { }` blocks were eliminated; API failures correctly bubble to display informative error dialogs.
- Legacy CRM (`CrmTransactionsForm.Operations.cs`) uses `OpenMechanicCopy`, mapping `job.InquiryNotes` directly and presenting the preview dialog.

### 2.2 Fix 2: Receipt Cashier Attribution & Historical Handling

#### Root Cause Analysis
Tenant A set `RecordedBy = api.Username`, confusing the current document viewer with the actor who originally took the customer's payment. Legacy CRM hardcoded `"System Administrator"`.

#### Resolution & Audit Trail Lookup
- **Trusted Write Path:** When payments are created via `POST /crm/payments`, `CRM.api/Program.cs` captures the authenticated user's name/ID in `db.AuditActor`. `WorkshopRules.cs` creates an immutable `AuditEntry` with `EntityType = "Payment"`, `Action = "Added"`, and `Changes` recording the payment's unique `SubmissionId`.
- **Attribution Retrieval:** The backend receipt endpoint (`GET /crm/payments/{id}/receipt`) looks up the `AuditEntry` matching the payment's `SubmissionId` and resolves the actor against `db.Staff` to retrieve their readable display name (or username).
- **Historical Attribution:** If no audit record exists (historical or pre-existing seed data), `recordedBy` displays `"Not recorded"`. The cashier is never inferred from the current logged-in user.
- **Printed By Separation:** The document viewer's identity upon printing is labelled separately under `Printed By:`, clearly distinguishing it from `Recorded By:`.
- **Legacy CRM:** `OpenPaymentReceipt` in `CrmTransactionsForm.Operations.cs` executes the identical audit lookup against `MasterCrmDbContext.AuditEntries`, displaying `"Not recorded"` when unrecorded.

### 2.3 Fix 3: Real Stale-Document Protection & DOM Correlation (`ReportPreviewDialogForm.cs`)

#### Root Cause Analysis & Correction of Previous Claims
An earlier implementation incremented `currentGeneration` in `SetDocument`, but `WebBrowser_DocumentCompleted` only checked `webBrowser.ReadyState == WebBrowserReadyState.Complete` without verifying that the loaded document matched that generation. Consequently, any document completion event (or sub-frame navigation) could re-enable `btnPrint` and `btnPageSetup` prematurely for an older document while a new document was still rendering.

#### Implemented Correlation Architecture
1. **Correlation Token Injection:**
   - In `SetDocument(title, html)`, a unique generation token is formed: `$"revcare-doc-{generation}-{Guid.NewGuid():N}"`.
   - `InjectDocumentToken` injects `<meta name="revcare-doc-token" content="{token}" />` into the HTML `<head>` tag.
2. **Immediate Reset of Readiness:**
   - Both `btnPrint.Enabled` and `btnPageSetup.Enabled` are set to `false`.
   - `lblStatus.Text` displays `"Rendering preview..."`.
3. **DOM Meta Tag Extraction:**
   - In `WebBrowser_DocumentCompleted`, `ExtractTokenFromDocument` traverses `doc.GetElementsByTagName("meta")` to find `name="revcare-doc-token"`.
   - In `ProcessDocumentCompleted(token, readyState)`:
     - If `token` is null, empty, or does not equal `currentDocumentToken`, the event is rejected as stale. Printing remains strictly disabled.
     - Only when `token == currentDocumentToken` AND `readyState == WebBrowserReadyState.Complete` are `btnPrint` and `btnPageSetup` enabled and status changed to `"Ready to print"`.
4. **Render Timeout Protection:**
   - A 10-second `System.Windows.Forms.Timer` is started on each `SetDocument`.
   - If rendering hangs or fails, `HandleRenderTimeout` fires, setting status to `"Document preview timed out. Printing remains disabled."` with red text and keeping print buttons disabled.
5. **Form Closing & Safe Disposal:**
   - On `OnFormClosing` and `Dispose`, `CancelPendingReadiness` stops the timer and clears `currentDocumentToken`, guaranteeing no background events re-enable printing or throw after form closure.

### 2.4 Fix 4: Removal of Fabricated Payment-Date Fallbacks

#### Root Cause Analysis
In `CRM_Revcare/TenantWorkspaceForm.cs`, line 790 previously contained:
```csharp
DateTime paymentDate = DateTime.TryParse(doc["paymentDate"]?.ToString(), out var dt) ? dt : DateTime.UtcNow;
```
If `doc["paymentDate"]` was missing or unparseable, this substituted `DateTime.UtcNow`, fabricating an inaccurate historical transaction date.

#### Resolution & Timezone Integrity
1. **Strict Validation Without Fallback:**
   In `TenantWorkspaceForm.OpenReceiptAsync`:
   ```csharp
   string rawDate = doc["paymentDate"]?.ToString();
   if (string.IsNullOrWhiteSpace(rawDate) || !DateTime.TryParse(rawDate, CultureInfo.InvariantCulture, DateTimeStyles.AdjustToUniversal | DateTimeStyles.AssumeUniversal, out var paymentDate))
   {
       MessageBox.Show(this, "The receipt cannot be displayed because the payment record is missing a valid transaction timestamp.", "Payment Validation Error", MessageBoxButtons.OK, MessageBoxIcon.Error);
       return;
   }
   ```
   In `CrmTransactionsForm.Operations.OpenPaymentReceipt`:
   ```csharp
   if (freshPayment.CreatedAt == default)
   {
       MessageBox.Show(this, "The receipt cannot be displayed because the payment record is missing a valid transaction timestamp.", "Payment Validation Error", MessageBoxButtons.OK, MessageBoxIcon.Error);
       return;
   }
   ```
2. **Explicit UTC Designation Across All Document Timestamps:**
   In `ReportTemplateBuilder.cs`, all receipt timestamps are explicitly formatted and designated with UTC via `FormatUtcTimestamp`:
   - **Payment Date:** `Payment Date: YYYY-MM-DD HH:MM UTC` (original transaction timestamp).
   - **Voided Date:** `Voided at: YYYY-MM-DD HH:MM UTC` (audit timestamp of void).
   - **Billing Calculation Time:** `Current Job Billing Summary (Calculated at YYYY-MM-DD HH:MM UTC)`.
   - **Print Date:** `Printed YYYY-MM-DD HH:MM UTC` in footer (reprint timestamp).
3. **Reprint Preservation:**
   When reprinting a payment days or weeks later, `Payment Date` remains the original historical date; only `Printed` in the footer reflects the reprint execution time. Stored records are never mutated.

### 2.5 Fix 5: Tenant-Scoped Business Details & Configuration Isolation

#### Root Cause Analysis
`ReportTemplateBuilder` previously relied on a mutable static `CurrentBusiness` property. Any caller modifying it would leak configuration across tenants or between Legacy and Tenant A sessions. Furthermore, unverified contact numbers and addresses were hardcoded in templates.

#### Resolution & Clean Separation
1. **Explicit Parameter Passing:**
   `CurrentBusiness` was marked `[Obsolete]` to discourage shared mutable state. Methods `BuildMechanicCopyHtml(data, business)` and `BuildPaymentReceiptHtml(data, business)` require or default to an independent `new BusinessDetails()` instance.
2. **Tenant A Configuration Flow:**
   - In `CRM.api` (`WorkforceEndpoints.cs` and `WorkshopEndpoints.cs`), tenant business details are resolved server-side:
     - Checked against `IConfiguration` section `Tenants:{tenantId}`.
     - Fallback to `PlatformMasterDbContext.Tenants` (`DisplayName`).
     - Default to `"RevCare Auto Hub"`.
   - The resolved `businessDetails` object (`name`, `tagline`, `address`, `contact`) is included directly in the authorized JSON responses for `GET /crm/workshop/jobs/{id}/work-order` and `GET /crm/payments/{id}/receipt`.
   - `TenantWorkspaceForm` extracts `doc["businessDetails"]` and passes it explicitly into `ReportTemplateBuilder`.
3. **Legacy CRM Configuration Flow (`LegacyBusinessConfig.cs`):**
   - Created `LegacyBusinessConfig.Load()` which reads `appsettings.json` section `LegacyBusiness` / `BusinessDetails` or falls back to RevCare defaults independently of the API.
   - Passed explicitly in `CrmTransactionsForm.Operations.cs`.
4. **Clean Omission & Security:**
   - When optional `Address` or `Contact` is null, `brand-sub` is omitted cleanly without orphan bullets (`&bull;`) or blank containers.
   - All business details (`Name`, `Tagline`, `Address`, `Contact`) are strictly HTML-encoded with `WebUtility.HtmlEncode()`.

### 2.6 Fix 6: Standardized Receipt Reference Search

#### Centralized Search Implementation
Added standardized helpers to `crm.domain.entities.Payment` and forwarded through `ReportTemplateBuilder`:
```csharp
public static string FormatReceiptReference(int paymentId) => paymentId > 0 ? $"RCPT-{paymentId:D6}" : "Pending Save";
public static string FormatUnpaddedReceiptReference(int paymentId) => paymentId > 0 ? $"RCPT-{paymentId}" : "Pending Save";

public static bool MatchesReference(int paymentId, string query)
{
    if (string.IsNullOrWhiteSpace(query) || paymentId <= 0) return false;
    query = query.Trim();
    string idStr = paymentId.ToString();
    string paddedRef = FormatReceiptReference(paymentId);
    string unpaddedRef = FormatUnpaddedReceiptReference(paymentId);

    return query.Equals(idStr, StringComparison.OrdinalIgnoreCase)
        || paddedRef.Contains(query, StringComparison.OrdinalIgnoreCase)
        || unpaddedRef.Contains(query, StringComparison.OrdinalIgnoreCase);
}
```
Integrated across both applications:
- **Legacy CRM (`CrmTransactionsForm.Operations.cs`):** `ConfigurePaymentList` evaluates `ReportTemplateBuilder.MatchesReceiptReference(row.PaymentId, query)`.
- **Tenant A (`TenantWorkspaceForm.cs`):** Payment grid filter evaluates `ReportTemplateBuilder.MatchesReceiptReference(pid, query)`.
- **Query Support:** Searches matching `RCPT-000001`, `RCPT-1`, `1`, `000001`, or `rcpt-` resolve reliably.

## 7. UI Optimization: Pre-Selection Removal, Header Readability, and Job Tasks Pop-Up

### A. Removal of Automatic Pre-Selection Across ALL Modules
- **Legacy CRM (`CrmCollectionController.cs` & `CrmTransactionsForm.cs`)**:
  - Previously, WinForms DataGridView default behavior auto-focused the first cell/row when a tab became visible or received focus, causing row 0 (e.g. Complaint #21 in the Complaints tab) to be highlighted and automatically enabling `Edit Selected` and `Delete / Deactivate`.
  - Fixed by configuring `Grid.TabStop = false` and adding lifecycle handlers (`page.VisibleChanged`, `Grid.Enter`, `Grid.DataBindingComplete`, tab button `CheckedChanged`, and form `Shown`) that clear selection and keep `CurrentCell = null` unless explicitly clicked by the user.
  - Action buttons (`Edit Selected`, `Delete / Deactivate`, `Preview Receipt`, etc.) remain safely disabled until an explicit user selection (`CellClick` / `FullRowSelect`) occurs.
- **Tenant A (`TenantWorkspaceForm.cs` & `TenantWorkspaceForm.Workshop.cs`)**:
  - Enforced `SelectedRows.Count > 0` validation before binding `selectedRecordId` or `selectedJobId`.
  - Cleared selection across `records` and `jobsOverview` on module switching, initial load, and search clear.

### B. Job Orders Grid Header Visibility & Auto-Resizing
- **Root Cause**: `JobOrderPage.Designer.cs` hardcoded `recordsGrid.ColumnHeadersHeight = 38`. Multi-line column headers such as `"Total Estimated Cost"`, `"Outstanding Balance"`, `"Customer Credit"`, and `"Turnaround Hours"` were vertically cut off on the second line, requiring users to drag or scroll the header down.
- **Fix Applied**:
  - Set `recordsGrid.ColumnHeadersHeight = 48` in Legacy CRM (`46` in Tenant A).
  - Set `recordsGrid.ColumnHeadersHeightSizeMode = DataGridViewColumnHeadersHeightSizeMode.EnableResizing`.
  - Configured `recordsGrid.ColumnHeadersDefaultCellStyle.WrapMode = DataGridViewTriState.True`.
  - Adjusted minimum column widths (`TotalEstimatedCost`: 125, `OutstandingBalance`: 125, `CustomerCredit`: 115, `TurnaroundHours`: 115, `CompletedAt`: 140, `EstimateId`: 135) to provide spacious, clean layout with zero text clipping.

### C. Dedicated Job Tasks Pop-Up Window
- **Architecture**:
  - Created `JobTasksDialogForm` (Legacy CRM) and `TenantJobTasksDialogForm` (Tenant A) providing a dedicated, full-size modal window for workshop task management.
  - Displays comprehensive job header details (Job Order #, Customer Name, Contact Number, Vehicle Display, Status, and Intake Instructions).
  - Features an unconstrained, high-resolution tasks grid displaying Task #, Service Name, Status, Review Status, Assigned Technician, and Inspection Remarks.
  - Provides instant progress updates (`Update Task Progress` / `Start Task` / `Mark Done` / `Submit Review`), remarks editing, and direct access to `[📋 Mechanic's Copy]` / `[📋 Work Order Copy]`.
  - Triggered by double-clicking any job row in the upper grid or by clicking the new `"📋 View Tasks (Pop-up)"` toolbar button.
  - Keeps underlying split master-detail grids synchronized so all existing tests and automated suites continue to pass without breaking changes.
